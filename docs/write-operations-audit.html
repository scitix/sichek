SICHEK · WRITE-OPERATIONS AUDIT

定时监控中的写操作审计 —— sichek 到底改了节点什么

sichek 的设计契约是「只采集 + 判断，不改变被检节点状态」。本页登记全部会改变系统状态的代码路径： 哪些是 daemon 每个 tick 都可能自动执行的隐式 autofix，哪些只在用户显式调用时发生，哪些有代码但当前休眠。 每一项给出写命令、调用链、触发条件与风险。

总览：写点分布

最重要的一条结论 A 类 5 处 autofix 的共同行为是「修好了就报 Normal」——上层（K8s annotation、Prometheus、snapshot）只能看到 DisabledOnline / LoadedOnline / EnabledOnline 这类字符串，看不到任何"发生过一次写操作"的事件。 换句话说：sichek 每 10 秒可能悄悄改 PCIe 寄存器、内核模块和 CPU 调频策略，且平台侧默认无感知。

A 类 · 生产路径自动执行的 autofix

以下 5 类动作全部挂在 collector / checker 上，daemon 每 tick（10s）与每次一次性 HealthCheck 都会重新评估。 共同特征：判定即修复，没有开关、没有 spec 守卫、没有 dry-run，全部以 daemon 的 root 权限执行。

A1 关闭全节点所有 PCIe 设备的 ACS 影响面最大上次审计误判为休眠

components/nvidia/checker/check_dependences/pcie_acs.go · pkg/utils/pcie_inspect.go · 自 2025-03-21 (10ea54f) 起在生产路径

nvidia 组件的 pcie-acs checker 每个 tick 扫描 /sys/bus/pci/devices 下的全部 PCIe 设备 （不限于 GPU / HCA——包括 PCIe switch、存储 NIC、任何插卡），对每个设备执行 setpci -s <BDF> ecap_acs+6.w 读取 ACS Control；只要发现非 0000，立即批量写 setpci -v -s <BDF> ecap_acs+6.w=0 关闭该设备 ACS。 

// pcie_acs.go:48-60（checker 主体）
enabledACS, err := utils.GetACSEnabledDevices(ctx)   // 扫全部 PCIe 设备
if len(enabledACS) > 0 {
    failedDevices, err := utils.BatchDisableACS(ctx, enabledACS)   // :56 批量写
    if err == nil && len(failedDevices) == 0 {
        result.Status = consts.StatusNormal          // 改完寄存器 → 报 Normal
        result.Curr   = "DisabledOnline"
    }
}

// pcie_inspect.go:99（实际写命令，DisableACS 内）
output, err := ExecCommand(ctx, "setpci", "-v", "-s", BDF, "ecap_acs+6.w=0")

调用链  nvidia HealthCheck / tick → PCIeACSChecker.Check（pcie_acs.go:47）→ GetACSEnabledDevices（pcie_inspect.go:66，逐设备 setpci 读）→ BatchDisableACS（:139）→ DisableACS（:92，写在 :99）

  • 影响面：ACS 控制 PCIe P2P 事务的重定向与隔离。虚拟化 / VFIO 直通环境依赖 ACS 划分 IOMMU group——被 sichek 静默关闭后，设备隔离边界改变；这正是"为裸金属 GPU P2P 调优"与"多租户隔离"互相冲突的开关，不应由健康检查 agent 单方面决定。
  • 静默：关闭成功即报 Normal / DisabledOnline，只有失败才 Abnormal——即"改了但没告警"。
  • 读侧噪声：即使无写发生，每 tick 也会对每个 PCIe 设备各 fork 一次 setpci 读（数百进程 / 10s）。

A2 改写 IB 网卡 PCIe Max Read Request 寄存器 两个触发点可能一 tick 写 3 次

components/infiniband/collector/pcie_info.go · components/infiniband/checker/pcie_mrr.go

同一个写函数 ModifyPCIeMaxReadRequest（pcie_info.go:460，写命令在 :490）现在有两个独立触发点—— 上次审计只记录了 collector 一处，checker 触发点为本次新增发现： 

// 触发点 ① collector：GetPCIEMRR（pcie_info.go:336-345）—— 读到 MRR≠4096 就写
if strings.Compare(mrr[0], "4096") != 0 {
    ModifyPCIeMaxReadRequest(bdf[0], "68", 5)          // :341
}

// 触发点 ② checker：PCIEMRRChecker.Check（pcie_mrr.go:101-110）—— 与 spec 不符就写
if hwInfo.PCIEMRR != hcaSpec.Hardware.PCIEMRR {
    result.Status = consts.StatusAbnormal
    collector.ModifyPCIeMaxReadRequest(hwInfo.PCIEBDF, "68", 5)   // :108 固定写 4096！
}

// 写实现（pcie_info.go:460-508）：读-改-写-回读，改的是 0x68 (Device Control) 高 4 位
writeCmd := exec.Command("setpci", "-s", deviceAddr, offset+".w="+writeValueStr)   // :490

调用链  IB HealthCheck / tick → IBHardWareInfo.Collect → GetPCIEMRR（ib_hardware_info.go:120 与 :121 被调两次）→ 写①；同一 tick 内 checker 再比对 spec → 写②。

  • 一 tick 最多写 3 次：collector 双调用（:120 判长度、:121 取值）各评估一次 autofix，checker 再来一次。
  • checker 触发点与 spec 自相矛盾：判断条件是 curr ≠ spec.PCIEMRR，但写入值硬编码 nibble 5（= 4096B）。若某机型 spec 基线不是 4096，将进入永久循环：每 tick 报 Abnormal → 写 4096 → 下 tick 依旧 ≠ spec → 再写。
  • 改的位比字段宽：函数覆写 bit 15:12，而 MRR 只是 bit 14:12；bit 15 是 Device Control 保留位。当前实参 5（0101）bit15=0 无副作用，若日后传 8–F 会连带改动 bit 15。
  • MRR 影响 PCIe 读事务大小与带宽公平性——运维按存储 / 网卡混插场景调低 MRR 的节点，会被 sichek 每 10s 改回 4096。

  • 顺带的状态 bug（:69-77）：写成功且回读通过的分支里，先赋 StatusNormal 又立刻被 StatusAbnormal + "failed to set" 文案覆盖——上报语义与实际动作相反，说明该路径缺测试。

A4 在线 modprobe nvidia_peermem

components/nvidia/checker/check_dependences/nvidia_peermem.go
// Check（:61-64）：ib_uverbs / ib_core 未持有 nvidia_peermem 就在线加载
if !usingPeermem {
    _, err := utils.ExecCommand(ctx, "modprobe", "nvidia_peermem")   // :62
    if err == nil { result.Curr = "LoadedOnline"; result.Status = Normal }
}
  • 加载内核模块改变内核状态；若正处于驱动升级 / 卸载窗口，在线 modprobe 可能与运维操作互相干扰。
  • 成功即报 Normal；nvidia config 里 check_items.go 中出现的 modprobe / setpci 字符串仅是 Suggestion 文案，不属于执行路径（勿混淆）。

A5 拉起 nvidia-persistenced 守护进程 上次审计未记录

components/nvidia/checker/check_gpu_persistence.go
// Check（:65-76）：逐 GPU 比对 persistence mode 与 spec，不一致就执行
for _, device := range nvidiaInfo.DevicesInfo {
    if device.States.GpuPersistenceM != c.cfg.State.GpuPersistenceM {
        _, err := utils.ExecCommand(ctx, "nvidia-persistenced")   // :69
    }
}
  • 该命令会以 root 启动一个常驻守护进程并使全部 GPU 进入 persistence mode——不是一次性的寄存器写，而是给节点添了一个 sichek 之外无人管理的进程。
  • 循环写在 per-GPU 判定里：8 卡节点若全部不达标，会连续 exec 8 次（后 7 次因端口 / socket 已占用而失败，靠失败兜底）。
  • 成功报 Normal / EnabledOnline，同样静默。

B 类 · 用户显式触发的写 / 负载注入

这些不在 daemon 定时路径上，只在用户敲命令时发生；列出是因为它们同样改变节点状态（负载或系统文件），使用时需要知情。

B1 sichek all 默认附带 NCCL 打流；nccltest / ib_perftest 注入负载

cmd/command/component/all.go:126-134 · nccl_perftest.go · ib_perftest.go · components/infiniband/perftest/
  • sichek all 在组件检查后会自动跑一轮 all_reduce（buffer 2G，bash 执行 nccl-tests，all.go:128），占用节点全部 GPU。在有训练任务的节点上执行一次性巡检时会与业务抢卡。
  • sichek ib_perftest 走 sh -c ib_write_bw/ib_read_bw ...（local_ibtest.go），对 IB 链路打满带宽。
  • daemon 定时路径不会触发这两者（已核实 cmd/command/daemon、service/ 无引用）。

B2 sichek daemon start|update 安装 systemd 资产并 restart

cmd/command/daemon/start.go:53 · update.go:53 · systemd/systemd.go:49-81 · pkg/systemd/systemd.go:106-151
  • 写 /etc/systemd/system/sichek.service、env 文件、logrotate 配置；执行 systemctl enable / daemon-reload / restart / stop。
  • 属部署意图内的写操作，风险点仅在与 DaemonSet 共存时：节点重启后 initContainer 会用镜像版覆盖手动安装的二进制（现场已多次踩坑）。

B3 gpuprobe 在空闲 GPU 上 exec CUDA kernel 做计算自检 默认关

components/gpuprobe/collector/runner.go · gating.go · probe/gpu_probe.cu
  • 不在 consts.DefaultComponents 里，daemon / sichek all 不会自动跑；只有用户显式 sichek gpu_probe 或 -E gpuprobe 才会加载并执行。
  • 空闲门控 + 探针自查双防线：collector 先核实目标 GPU 无计算进程、显存空闲率与利用率达标（min_free_mem_pct / max_gpu_util_pct），判定忙的卡直接跳过、绝不 exec；探针自身在 CUDA 层再做一次同类判定，命中忙/OOM 时以 SKIP 退出而不是抢占。忙卡全程不碰。
  • 即使命中空闲，也是短时占用（一次 kernel launch + 校验，`probe_timeout_sec` 兜底强杀），不同于 B1 的全带宽打流。

C 类 · daemon 自有状态写

属既定职责、不算违背契约，列出是为了画清信任边界；其中 C1 有一个已在现场造成过事故的边界问题。

C1 config / spec 下载会覆写生产 canonical 路径 一次性 CLI 也会写

components/common/spec.go:299-351,428 · pkg/httpclient/httpclient.go:127,218

共性问题

五个 A 类写点的共同模式
  • 判定即修复：把"修复"写进了 collector / checker，没有独立的 remediation 层。
  • 无任何守卫：没有全局 autofix 开关、没有 per-checker 开关、没有 dry-run、spec 里也没有对应字段。
  • 修好即静默：成功路径上报 Normal（*Online 后缀是唯一痕迹），annotation / metrics / snapshot 均无"写操作发生"事件。
  • 高频重试：默认 10s tick，一旦条件持续成立（如 A2 的 spec≠4096 场景）就变成周期性寄存器写。
  • root + 全集群：以 DaemonSet 形式跑在每个节点上，任何误判都会被放大到集群规模。

与 2026-07-09 审计的差异

PCIe ACS 关闭 "仅测试调用，生产路径无人触发"（休眠） 更正：误判。PCIeACSChecker 自 2025-03-21 起注册在 nvidia 生产 checker 表（checker.go:31）且默认启用，经 BatchDisableACS 每 tick 可对全节点 PCIe 设备执行 ACS 关闭 → 升级为 A1。前次只查了 DisableACS/DisableAllACS/EnableACS 的 caller，漏掉了 BatchDisableACS。
PCIe MRR 改写 1 个触发点（collector GetPCIEMRR）+ 双调用 发现第二个触发点：checker pcie_mrr.go:108（且写入值与 spec 判定条件矛盾）→ A2 扩充。

CPU governor / nvidia_peermem 已记录 行为不变（行号更新：governor 写点现为 :167-174）。

建议（待决策，未实施）

  • 统一 autofix 开关：为 A1–A5 加全局 + per-checker 的 autofix.enable（默认 false），恢复"只读健康检查"缺省语义；开启时在 CheckerResult 里显式记录 "performed write: <cmd>"，让 annotation / metrics 可见。
  • A1 优先处理：ACS 关闭影响面横跨全节点 PCIe 设备，建议先改成"只报不改"（Abnormal + Suggestion），把关 ACS 留给部署 playbook。
  • 修 A2 的两个逻辑错误：GetPCIEMRR 双调用改为取一次复用；checker 的写入值应取自 spec 而非硬编码 4096（或干脆移除 checker 内的写，只留判定）；ModifyPCIeMaxReadRequest 收窄为只改 bit 14:12。
  • 修 A3 的状态上报 bug（cpu_performance.go:69-77 覆写分支）。
  • B1 解绑：sichek all 默认不跑 nccltest，改为显式 --with-nccltest。
  • C1 收敛：一次性 CLI 带 -c/-s 时落盘到临时目录而非 /var/sichek/config。
